# Спринт 1. Задание 1 "Проект Mesto"

## Уровень 1. Проектирование

### Предварительный анализ

1. *Бизнес-требования*. Учитывая текущий функционал приложения — загрузку, редактирование
   фотографий и сбор лайков — можно предположить, что оно будет развиваться в сторону полноценной
   социальной сети. Это подразумевает необходимость быстрой разработки и внедрения нового
   функционала. Её реализация потребует расширения API и добавления новых компонентов, таких как
   список друзей и новостная лента. Также пользователи, скорее всего, захотят комментировать
   фотографии и выражать реакции помимо лайков. В дальнейшем может возникнуть потребность в более
   сложной логике для определения популярных фото, системе уведомлений о новых реакциях и других
   подобных возможностях.
2. *Нефункциональные требования*. Приложение реализовано как одностраничное с использованием
   всплывающих окон. Дизайн приложения должен оставаться гибким и готовым к изменениям. Для
   обеспечения качественного пользовательского опыта имеет смысл отслеживать производительность
   интерфейса — возможно, потребуется кэширование пользовательских данных или самих изображений.
   Также мониторинг помогает выявлять проблемы с UX и получать представление о реальных трудностях,
   с которыми сталкиваются пользователи на своих устройствах.
3. *Кодовая база*. Анализ кода показывает потенциальные проблемы, связанные с высокой
   степенью связности между отдельными компонентами. Например, запросы к API для получения данных о
   пользователе и карточках выполняются одновременно при монтировании, хотя эти операции не
   обязательно должны быть связаны — загрузку информации о пользователе можно вынести отдельно.
   Кроме того, компонент PopupWithForm используется во многих частях приложения, и любые изменения в
   его реализации затрагивают большое количество других компонентов, что усложняет поддержку и
   развитие кода.

### Предлагаемое решение

На основании изложенных требований можно выделить ключевые проблемы текущего состояния проекта:

+ Высокая связность компонентов затрудняет внедрение нового функционала и повышает риск появления
  ошибок.
+ По мере роста команды усложняется процесс внесения изменений из-за сложной интеграции между
  компонентами.
+ Возможно, будет полезно иметь возможность отладки, логирования и мониторинга на
  уровне отдельных компонентов, что упростит диагностику и сопровождение системы.

Переход на микрофронтендную архитектуру с вертикальной нарезкой понизит связанность компонентов и
повысит параллелизм разработки. Предлагаемое разделение:

- **cards** работа с фото
- **profile** работа с профилем
- **auth** аутентификация и авторизация
- другие

Для реализации предлагается использовать фреймворк Single SPA, который позволит организовать
приложение по принципу микрофронтендов. Это решение даёт ряд ключевых преимуществ:

+ Разделение команды на небольшие автономные группы, каждая из которых будет отвечать за отдельный
  функциональный модуль. Это ускорит разработку новых функций и упростит процесс интеграции.
+ Гибкость в выборе технологий: разные команды смогут использовать наиболее подходящие инструменты и
  библиотеки, включая специализированные решения для логирования и мониторинга.
+ Пошаговая интеграция изменений — благодаря изолированной разработке компонентов, новые части
  приложения можно внедрять постепенно, без риска нарушить уже работающий функционал.
+ Клиентская композиция компонентов в runtime обеспечит динамичность интерфейса и независимость
  обновлений, что особенно важно для приложения, отображающего фотоконтент и предполагающего
  активную пользовательскую вовлечённость.

Для организации взаимодействия между микрофронтендами предлагается использовать событийную шину и
паттерны Pub/Sub, что обеспечит слабую связанность компонентов при сохранении эффективной
коммуникации. Это также упростит реализацию централизованного логирования и мониторинга.

Так как используется Single SPA, маршрутизацию целесообразно реализовать на клиентской стороне. Это
не требует существенных усилий на реализацию, при этом улучшает отзывчивость интерфейса и общее
качество пользовательского опыта.

## Уровень 2. Планирование изменений

Предлагается следующая структура компонентов:

- Приложение **cards** отвечает за редактирование фотографий и включает:
    - *AddPlacePopup* и - добавление фото
    - *Card* - интерфейс для работы с фото
    - *ImagePopup* - отображение фото

- Приложение **profile** выполняет работу с профилем пользователя и включает:
    - *EditProfilePopup* - редактирование профиля
    - *EditAvatarPopup* - редактирование аватара

- Приложение **auth** отвечает за авторизацию пользователей
    - *Login* - отправка логина и пароля
    - *InfoTooltip* - результат авторизации
    - *Register* - регистрация нового пользователя

- Приложение **root**
    - *Header* - но нужно избавиться от зависимостей от компонентов auth и оставить только
      маршрутизацию
    - *Footer*

- Общие библиотеки приложений (если объем общих компонентов увеличится, то можно рассмотреть
  возможность использование фреймворка **ModuleFederation**)
    - *PopupWithForm*
